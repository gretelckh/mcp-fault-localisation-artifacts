```text
Check that mcp.server.auth.middleware.bearer_auth._send_auth_error constructs WWW-Authenticate
```

## 2. What the reporter described

When RequireAuthMiddleware's _send_auth_error constructs WWW-Authenticate, it includes only error/error_description (optionally resource_metadata) and never the scope= parameter required by RFC 6750, so the client cannot determine the scope required for re-authorization from the challenge.

## 3. What we captured

Captured in our run (evidence tier B).

```
_send_auth_error: www_auth_parts=[error, error_description(, resource_metadata)] -> Bearer ...; the scope= parameter is missing
```

## 4. Why it happens

When `RequireAuthMiddleware._send_auth_error` constructs `WWW-Authenticate`, it includes only error/error_description (optionally resource_metadata) and never the `scope=` parameter required by RFC 6750 §3; the client cannot learn the required scope when re-authorizing from the challenge, so the step-up authorization scope is downgraded. It is reported at the Server layer (the correct layer), but the challenge information is downgraded — a single-layer generalization/masking.
